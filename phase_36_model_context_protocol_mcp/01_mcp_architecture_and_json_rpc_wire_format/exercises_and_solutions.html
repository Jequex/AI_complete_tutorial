Interactive exercises covering JSON-RPC 2.0 error handling, batching rules, and transport isolation.

Exercise 1: Standard Error Code Resolution

An MCP server receives four problematic payloads: invalid param types, unregistered method, missing jsonrpc: "2.0", and corrupted syntax. For each, determine the error code and whether the id is preserved.

Click to Reveal Solution & Explanation
  • SQL integer instead of string: Error -32602 (Invalid params), preserves request id.
  • Unregistered method name: Error -32601 (Method not found), preserves request id.
  • Missing jsonrpc: "2.0": Error -32600 (Invalid Request), preserves request id if syntactically parsed.
  • Corrupted JSON syntax: Error -32700 (Parse error), id is null because JSON parsing failed before token extraction.

Exercise 2: Batch Processing Protocol Rules

A client submits a 4-item batch containing 2 requests and 2 notifications. How many responses are returned, and what happens if an empty array [] is dispatched?

Click to Reveal Solution & Explanation

Answer: Exactly 2 response objects are returned. Under JSON-RPC 2.0, notifications (items without an id) must never generate response elements, even within a batch.

Sending an empty batch [] causes an immediate single error response with code -32600 (Invalid Request).

Exercise 3: Stdio Subprocess Contamination Prevention

Why does a raw print("Connecting...") statement break an MCP stdio server, and how should logging be implemented?

Click to Reveal Solution & Explanation

Answer: The stdio transport frames JSON-RPC messages line-by-line over stdout. Raw text corrupts the JSON parser, causing -32700 Parse error and disconnection.

Developers must redirect debugging text to sys.stderr (which the host client isolates) or emit structured notifications/message JSON-RPC notifications over stdout.
