Topic 28.3: 3D Parallelism & ZeRO Sharding

Mastering large-scale model training: the 3D Parallelism Triad (Data, Pipeline, Tensor) and DeepSpeed ZeRO-1/2/3 memory partitioning.

12-Year-Old Intuition: The Giant Book Factory

Imagine printing a 10,000-page encyclopedia that exceeds the physical memory of any single press:

  • Data Parallelism: Multiple identical presses printing different customer orders simultaneously, then comparing notes. Fails when the book itself is too big for one press.
  • Pipeline Parallelism: An assembly line where Press 1 prints Chapter 1, passes it down a conveyor to Press 2 for Chapter 2, and so on. Idle startup and drain time is the Pipeline Bubble.
  • Tensor Parallelism: For an ultra-wide panoramic photo that doesn't fit on one press, Press A prints the left half and Press B prints the right half simultaneously, taped together instantly (NVLink).
  • ZeRO Sharding: Instead of every worker keeping a massive full dictionary on their desk ($16\Phi$ states), they split the dictionary into 8 slices. Workers fetch slices on demand and discard them immediately.

The Model State Memory Crisis ($16\Phi$ Bytes)

In standard mixed-precision training (FP16/BF16 weights and FP32 Adam):

  • FP16 Parameters: $2\Phi\text{ bytes}$
  • FP16 Gradients: $2\Phi\text{ bytes}$
  • FP32 Adam States: Master weights ($4\Phi$) + First Momentum ($4\Phi$) + Second Momentum ($4\Phi$) = $12\Phi\text{ bytes}$
$$\text{Total Model States} = (2 + 2 + 12)\Phi = 16\Phi\text{ bytes}$$

For a 70B parameter model (LLaMA-70B), model states alone consume $16 \times 70\text{ GB} = \mathbf{1{,}120\text{ GB}}$, requiring at least 14 80GB GPUs just to hold the weights and optimizer!

The 3D Parallelism Triad

$$\text{Total GPUs } N = \text{Data Parallel } (D) \times \text{Pipeline Stages } (p) \times \text{Tensor Parallel } (T)$$

1. Data Parallelism (DDP)

Replicates the model across $D$ workers. PyTorch DDP uses asynchronous bucketed All-Reduce ($\sim 25\text{ MB}$ chunks) overlapping gradient communication with backward computation.

2. Pipeline Parallelism (PP) & Bubble Schedules

Splits $L$ layers across $p$ sequential stages. Micro-batching ($m \gg p$) reduces idle bubbles:

  • Bubble Fraction: $F = \frac{p - 1}{m + p - 1} \approx \frac{p - 1}{m}$. To keep bubble $< 10\%$, use $m \ge 8p$.
  • GPipe vs. 1F1B: GPipe runs all forward passes then all backward passes, requiring $\mathcal{O}(m)$ activation memory. 1F1B alternates one forward and one backward, capping activation memory at $\mathcal{O}(p)$.

3. Tensor Parallelism (TP: Megatron-LM)

Partitions linear weight matrices within each layer:

  • Column-Parallel ($W_1$): Splits columns; outputs pass through non-linearity without communication.
  • Row-Parallel ($W_2$): Splits rows; requires exactly one All-Reduce at the end of the block.
  • Restricted to intra-node NVLink ($900\text{ GB/s}$ and $T \le 8$) due to high per-layer communication frequency.

ZeRO: Zero Redundancy Optimizer

Stage Partitioned States Memory per GPU Communication Volume Memory for 70B ($N=64$)
Baseline DDP None (Replicated) $16\Phi$ $2\Phi$ (All-Reduce) $1{,}120.0\text{ GB}$ (OOM)
ZeRO-1 ($P_{os}$) Optimizer States $4\Phi + \frac{12\Phi}{N}$ $2\Phi$ ($0\%$ increase) $293.1\text{ GB}$
ZeRO-2 ($P_{os+g}$) Optimizer + Gradients $2\Phi + \frac{14\Phi}{N}$ $2\Phi$ ($0\%$ increase) $155.3\text{ GB}$
ZeRO-3 ($P_{os+g+p}$) Optimizer + Grads + Params $\frac{16\Phi}{N}$ $3\Phi$ ($1.5\times$ increase) $\mathbf{17.5\text{ GB}}$ (Fits in 80GB!)

How ZeRO-3 Works at Runtime

Parameters are sharded across all GPUs. During the forward pass, a layer issues an asynchronous All-Gather to assemble its weights, executes the matrix multiplication, and immediately deallocates the weights. During the backward pass, weights are gathered again to compute input gradients, followed by a Reduce-Scatter to partition gradients. This trades a modest $1.5\times$ network overhead for linear $N$-fold memory scaling.
